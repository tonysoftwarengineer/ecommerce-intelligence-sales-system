# ADR-005: RAG Is a Bounded Explanation Layer

**Status:** Accepted  
**Date:** 2026-08-20  
**Deciders:** Project owner

## Context

The implemented system calculates financial metrics, forecasts, diagnostics,
confidence, limitations, and recommendation priority through deterministic
Python code. Its typed evidence contract makes these outputs auditable.

A future retrieval-augmented generation (RAG) feature could help a business
connect those validated outputs with qualitative documents such as policies,
supplier notices, product catalogues, or approved operating calendars. However,
an unbounded model could invent calculations, treat an irrelevant document as
proof, expose another customer's content, follow prompt injection in a
document, or present correlation as cause.

The current application also lacks customer authentication, tenant-scoped
durable storage, and document governance. Therefore this decision defines the
integration boundary before any provider or vector database is selected.

## Decision

RAG will be introduced, if validated, as an optional bounded explanation layer
after deterministic analysis. The typed diagnostic report remains the only
authority for financial values, diagnostic status, confidence, limitations,
and recommendation priority.

The explanation path will:

1. Load an immutable validated analysis snapshot.
2. Retrieve only approved, versioned documents within the authenticated
   tenant's authorized scope.
3. Treat retrieved excerpts as untrusted contextual data, never instructions.
4. Require a typed model response with diagnostic evidence references,
   document citations, uncertainties, and human-reviewed investigations.
5. Run a deterministic verifier over numerical claims, references, citations,
   and prohibited language.
6. Fall back to the existing deterministic report if retrieval, generation, or
   verification fails.

Raw transaction rows will remain in structured analytical storage and will not
become the RAG calculation path. There will be no autonomous agent loop and no
tool that lets the model execute business actions.

No RAG code is added by this ADR. Authentication, tenant authorization,
durable document storage, retention rules, and a representative evaluation
corpus are prerequisites for implementation.

## Options considered

### Option A: Let an LLM analyze the uploaded CSV directly

| Dimension | Assessment |
|---|---|
| Implementation speed | High |
| Numerical reliability | Low |
| Auditability | Low |
| Security surface | High |

**Pros:** Quick prototype and flexible natural-language output.  
**Cons:** Weak reproducibility, difficult row-level grounding, unreliable
financial arithmetic, and unclear handling of ambiguous business rules.

### Option B: Use RAG as a bounded explanation layer

| Dimension | Assessment |
|---|---|
| Implementation speed | Medium |
| Numerical reliability | High when verifier invariants hold |
| Auditability | High |
| Security surface | Contained but meaningful |

**Pros:** Preserves the trusted calculation path while adding approved business
context and citations. Provider adapters can change without changing domain
logic.  
**Cons:** Requires identity, document governance, retrieval evaluation, output
verification, and additional latency and cost.

### Option C: Do not use RAG

| Dimension | Assessment |
|---|---|
| Implementation speed | Highest |
| Numerical reliability | High |
| Contextual explanation | Limited |
| Operating complexity | Lowest |

**Pros:** Smallest attack surface and simplest product.  
**Cons:** The system cannot safely incorporate business-specific policies or
documented events into explanations.

## Trade-off analysis

Option B is accepted as the future boundary, but not as an immediate feature.
It gives RAG a narrow job that structured analytics cannot perform well:
retrieving and explaining qualitative business context. The cost is that RAG
must wait for product evidence and production data boundaries.

This decision deliberately values faithfulness and graceful abstention over a
more conversational but less auditable assistant. If users only need the
deterministic dashboard, Option C remains a valid product outcome; the
architecture does not require an LLM to function.

## Consequences

- Existing calculations and diagnostics remain provider-independent.
- The dashboard remains useful during model, retrieval, or provider failure.
- Numerical statements generated by a model must match structured evidence.
- Document claims require citations to authorized sources.
- Unavailable diagnostics cannot be upgraded by model confidence or prose.
- Tenant isolation and prompt-injection defenses become release-blocking tests.
- Model quality is evaluated on faithfulness, abstention, citation quality,
  usefulness, latency, and cost—not only fluent wording.
- An explanation endpoint and vector store must not be added before identity,
  authorization, retention, and document ownership are designed.
